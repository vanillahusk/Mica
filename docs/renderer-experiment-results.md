# 新渲染技术实测 · 2026-10-01

> 后续状态：Merman Worker 已升级为默认“现代绘图”路径，使用 Neo 视觉与 ELK 排版；Mermaid 12 保留为用户主动选择的兼容路径。正式路径包含 8 秒父线程超时、取消、队列上限和手动兼容回退。下文仍保留最初实验快照，不把历史数据重写成正式版数据。

## 结论与落地

1. **已进入本地正式版 0.4.1：稳定高度的图表预览。** 延迟绘图不再推走下方正文；复杂大图通过已有查看、全屏、独立窗口入口阅读。
2. **保留当前屏幕外跳过排版策略。** 本次长文测试中优于整篇一次性排版，跳转后没有观察到锚点漂移。不代表所有图片/公式/文档都无位移。
3. **Merman WASM + Worker 有明确收益，但仍为实验。** 中等图表更快，父线程可强制终止 Worker；经过 SVG 输出适配后，有限样本的标签检查全部通过。复杂压力图触发资源保护，且 WASM 体积较大，不作为默认引擎。
4. **Sätteri 原生解析值得继续关注，但不直接替换 markdown-it。** 纯解析更快，不代表整个阅读过程快相同倍数；Mica 的提问目录、公式和自定义语法需要另行适配。

本轮没有把实验引擎、实验依赖、测试忙循环或实验服务器打进正式应用，没有更改远程仓库。正式版当前 Mermaid 仍在阅读页面线程执行；实验里的硬超时和 Worker 取消机制**尚未进入正式版**。

## 环境与方法

- Windows 10.0.26100，Intel Core i7-13700HX；Edge 154.0.4258.37。
- Mermaid 12.0.0、Merman Web Render 0.8.0-alpha.7、Sätteri 0.10.5，依赖版本锁定。
- 图表每种方案使用独立测试浏览器；普通图表覆盖中文流程、时序、类、ER、状态、思维导图、嵌套分组、长中文标签，以及一个错误语法样本。
- 中等图为 25 节点；压力图为 120 节点 / 240 边、包含循环。每种复杂度测量五次，表格为中位数。
- “显示完成”包含生成 SVG、相同 SVG 清理、插入 DOM 及等待两次 requestAnimationFrame。心跳为主线程每 10 ms 的计时器，统计每轮最大间隔，再取五轮中位数，不是实际显示器 FPS。
- 初次调用没有清空操作系统磁盘/代码缓存；只做一次，不能作为整机冷启动结论。
- 脚本、样本、固定依赖见 `ReaderWeb/experiments`；本机原始 JSON 和截图在其 `output` 目录，重新运行会更新。这里是本次快照，不是跨硬件性能承诺。

## 图表：速度、阻塞与兼容性

| 方案 | 中等图生成 SVG | 显示完成 | 主线程最大心跳间隔 | 标签/错误检查 |
| --- | ---: | ---: | ---: | ---: |
| 当前 Mermaid，主线程 | 105.0 ms | 112.4 ms | 64.9 ms | 9/9 |
| Merman，主线程 | 13.2 ms | 25.3 ms | 20.8 ms | 7/9 |
| Merman，Worker，默认输出 | 14.6 ms | 26.6 ms | 11.8 ms | 7/9 |
| Merman，Worker，resvg-safe 输出 | 21.1 ms | 32.4 ms | 15.3 ms | 9/9 |

Merman 默认输出的 ER、思维导图含 HTML 形式的标签，与当前禁止 foreignObject 的清理策略不兼容；不是两类图完全不受支持。使用其 `resvg-safe` 输出先转换为 SVG 文字，才解决标签缺失。截图核验覆盖中文流程、思维导图和长中文换行；主题背景、配色和其他图形仍需更全面的视觉回归，不能将标签存在等同于完整像素一致。

压力图：当前 Mermaid 显示完成约 749.9 ms，主线程最大心跳间隔约 359.4 ms。Merman 的三条路径均在 interactive 资源策略下报 `max_layout_work_units` 上限错误，**不把拒绝绘制算作加速成功**，也没有为了通过测试而放宽安全上限。

### 硬终止测试

在实验 Worker 中注入五秒忙循环，父线程的 100 ms 超时于约 101 ms 终止 Worker；其间主线程心跳运行了十次。重建 Worker 后可以正常绘图，模拟切换文档也可取消正在执行的任务。

这证明所写父线程终止机制可工作，不是发现了 Merman 本身会死循环，也不等于正式阅读器已有硬超时。主线程 WASM 调用仍不能靠同线程计时器强制抢占。

### 体积与内存

Merman 本次安装的 WASM 文件为 11,096,197 字节（约 10.6 MiB），尚不含 JS 与其他文件。它是增量依赖，不能当作零成本替代。

相同普通图表集和中等图工作量结束后的**测试 Edge 进程树 Working Set 合计**：

| 方案 | 初始化页面时 | 中等图测试后 |
| --- | ---: | ---: |
| Mermaid 主线程 | 471.1 MiB | 641.5 MiB |
| Merman 主线程 | 461.1 MiB | 595.6 MiB |
| Merman Worker | 465.2 MiB | 608.6 MiB |
| Merman Worker + resvg-safe | 444.2 MiB | 604.6 MiB |

该指标含浏览器固定开销，共享内存可能重复计入；不等于 Mica 的内存，更不能当作各库本身的内存。只有单次进程树快照，起点也有差异，暂不足以宣布某方案更省内存。复杂压力图一方成功、一方拒绝后的内存不直接比较。

## 长文排版与阅读稳定性

151,500 字符 / 1,500 个标题，五次测试：

| 策略 | 首屏中位数 | 正文挂载完成中位数 | 跳转后 400 ms 内锚点位移 |
| --- | ---: | ---: | ---: |
| 当前 content-visibility 跳过屏幕外排版 | 52.6 ms | 181.5 ms | 0 px |
| 强制整篇排版 | 98.7 ms | 353.7 ms | 0 px |

两者均使用当前后台解析、清理与分批插入，不把解析器差异混入测试。这里不测实际硬件滚动 FPS，也不声称实现了完整虚拟列表。

另一个独立测试：页面顶端图表先显示占位，再完成一张 15 节点纵向图的渲染。旧式自适应高度使其下方标题下移 **1,101 px**；固定 280 px 预览区域后为 **0 px**。采用该改进后，通过浏览器回归验证大图仍可在放大查看器中完整查看，并通过 WPF/WebView2 的目录、全屏恢复、独立窗口、编辑草稿和切换取消检查。

## Markdown 解析实验

同一份 151,500 字符文档；预热后 20 次，在 Node.js 里直接生成 HTML：

| 路径 | 中位数 | P95 |
| --- | ---: | ---: |
| 基础 markdown-it | 29.1 ms | 34.5 ms |
| Sätteri 原生 Rust 绑定 | 4.1 ms | 4.5 ms |
| Mica 当前完整解析（含目录和自定义输出） | 34.1 ms | 40.6 ms |

基础 markdown-it 与 Sätteri 在该样本都输出 309,000 字符；Mica 输出 523,888 字符，含额外工具栏等结构，因此第三行工作量不同。Sätteri 的默认 GFM 和 Mica 的高亮、上下标、QUESTION 提问块等语义不完全一致，不能只替换函数而保持现有阅读能力。

**本轮没有实测 Sätteri 的 WASM 路径或 .NET IPC 整体集成，也没有实现实时消息的增量 DOM 更新。** 这些仍是候选，不列为完成能力。

## 下一步建议

如继续集成图表隔离，应先增加真实文档图表语料和视觉回归，再设计“Worker 引擎优先、失败后由读者选择兼容渲染”的策略，避免自动回退到主线程后再次造成无提示卡顿。不要仅根据当前九个样本切换默认引擎。
